# THYME_DOMAIN_MODEL.md

# Thyme Domain Model

**Project:** Thyme  
**Artifact:** Domain Model  
**Version:** 0.1  
**Status:** Implementation foundation  
**Date:** 2026-08-16

> This document defines the conceptual domain model for Thyme. It is intentionally independent of a specific database engine, ORM, UI framework, or programming language. Clinical terminology and jurisdiction-specific requirements must be validated by ophthalmologists and qualified compliance specialists.

---

# 1. Domain goals

Thyme must model ophthalmology directly rather than treating it as generic patient notes. The core concepts are:

- Patient identity
- Encounters
- Eye/laterality
- Clinical observations and measurements
- Ophthalmic examinations
- Problems and diagnoses
- Diagnostic orders/results
- Imaging studies
- Medications and prescriptions
- Optical prescriptions
- Procedures and surgery
- Longitudinal history
- Documents and notes
- Scheduling, referrals, tasks and follow-up
- Users, roles and organizations
- Devices and device imports
- Provenance and audit
- External identifiers and terminology mappings

The model must preserve clinical history instead of overwriting it.

# 7. Eye and laterality

Laterality is a controlled domain value:

```text
OD = right eye
OS = left eye
OU = both eyes
NA = not applicable
UNK = unknown
```

Every eye-capable clinical object must explicitly support laterality.

The model must distinguish:

- Patient-level information
- Encounter-level information
- Eye-level information
- Bilateral information
- Anatomical-site information

`OU` does not necessarily mean "duplicate an OD record and an OS record." Some bilateral observations are intrinsically bilateral.

# 30. Domain invariants

1. **Eye-specific records require explicit laterality.**
2. **OU is not automatically equivalent to two independent observations.**
3. **Signed clinical records are immutable; corrections create amendments/versions.**
4. **Historical measurements are not overwritten by newer values.**
5. **Final prescriptions are separate clinical artifacts from refraction measurements.**
6. **Imported diagnostic data retains source identity and provenance.**
7. **Internal patient identity is independent from external IDs.**
8. **Clinical concepts are independent from billing codes.**
9. **Appointments do not prove clinical care occurred.**
10. **AI-generated suggestions are not clinical truth until explicitly reviewed/accepted.**
11. **A clinical fact must be attributable to an actor, source device, or source system.**
12. **All clinically meaningful timestamps must preserve their event semantics; creation time is not necessarily observation time.**

# 33. Clinical aggregate example

A glaucoma follow-up should be representable as:

```text
Patient
  └── Encounter
       ├── History
       ├── VisualAcuity OD/OS
       ├── Tonometry OD/OS
       ├── SlitLampExam OD/OS
       ├── FundusExam OD/OS
       ├── DiagnosticOrder
       │     ├── VisualField
       │     └── OCT
       ├── Diagnosis → Glaucoma Problem
       ├── MedicationPrescription
       ├── CarePlan
       └── FollowUp
```

A later visit can compare these records without copying them into a single "current state" blob.

# 34. Final domain test

The domain model should make this question natural:

> **For this patient, what happened to each eye, when did it happen, what was measured, what evidence supports it, what did the clinician conclude, what treatment was provided, and what changed afterward?**

If that question requires parsing giant text blobs or reconstructing state from unrelated records, the domain model is incomplete.
